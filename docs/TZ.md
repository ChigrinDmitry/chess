# ТЗ: Chess Online (frontend)

## 1. Цель и границы

Веб-приложение для игры в шахматы онлайн с другим человеком или с ботом в стиле **liquid glass**.

**В рамках этапа:** только фронтенд (React + TypeScript, архитектура FSD), включая игру с ботом в браузере и **архитектурную готовность к авторизации** (§5.2).
**Вне рамок:** сам бэкенд, вход/регистрация (в MVP только **гость**), профиль и история на сервере, рейтинг (Elo), матчмейкинг, база партий, анти-чит.

Бэкенда нет, поэтому:

- «онлайн» реализуется через **абстракцию транспорта** (§5.1): сейчас — мок-транспорт, позже — WebSocket без переписывания UI;
- личность игрока реализуется через **абстракцию сессии** (§5.2): сейчас — только гость, позже — реальный провайдер без переделки приложения.

## 2. Пользовательские сценарии

1. Открыть сайт → «Создать игру» → выбрать контроль времени и цвет → получить ссылку-приглашение.
2. Второй игрок открывает ссылку → занимает свободный цвет → партия начинается.
3. Играть: ходить, видеть ход соперника в реальном времени, следить за часами.
4. Завершить партию: мат, пат, время, сдача, ничья по соглашению или по правилам (3-кратное повторение, 50 ходов, недостаточный материал).
5. Просмотреть ходы партии после окончания.
6. Играть локально на одном устройстве (hot-seat).
7. **Играть против бота:** выбрать уровень, цвет, контроль времени → партия сразу начинается.
8. **Играть как гость:** без регистрации, с автоматически созданным ником; ник можно сменить. Недавние партии хранятся в браузере.

## 3. Функциональные требования

### 3.1 Шахматные правила

- Полные правила: рокировка, взятие на проходе, превращение пешки, шах/мат/пат, все виды ничьих.
- Правила **не пишем сами** — `chess.js`, изолированный за интерфейсом в `entities/game`.
- Нотация: SAN в списке ходов, FEN/PGN для экспорта.

### 3.2 Доска

- Ходы кликом (выбрал фигуру → выбрал клетку) **и** перетаскиванием (pointer events, touch).
- Подсветка: выбранная фигура, легальные ходы (точки/кольца для взятий), последний ход, шах.
- Переворот доски; ориентация автоматически по цвету игрока.
- Превращение пешки: диалог выбора фигуры.
- Анимация перемещения фигур.
- Координаты (a–h, 1–8).
- Управление с клавиатуры и ARIA-разметка (§4).
- Premove — не в MVP.

### 3.3 Партия

- Шахматные часы: blitz 3+2, 5+0, rapid 10+0, 15+10, без часов; инкремент.
- Список ходов с навигацией (← →, клик по ходу); просмотр истории не мешает ходить (кнопка «к текущей позиции»).
- Панели игроков: имя, аватар, цвет, время, взятые фигуры и материальный перевес.
- Действия: сдаться, предложить ничью (принять/отклонить), реванш.
- Модалка результата: итог, причина, «Реванш» / «Новая игра» / «Скопировать PGN».

### 3.4 Онлайн-часть (фронтовая)

- Создание комнаты, ссылка `/game/:id`, ожидание соперника.
- Синхронизация ходов, часов, предложений ничьей/сдачи через транспорт.
- Индикатор соединения; автопереподключение и восстановление позиции (resync по FEN + список ходов).
- Состояние «соперник отключился».

### 3.5 Игра с ботом

- Движок работает **в браузере** в Web Worker (UI не блокируется).
- Уровни сложности 1–8 (соответствуют силе игры от новичка до ~2000 Elo); настройка: уровень, цвет (белые/чёрные/случайно), контроль времени.
- Бот «думает» с небольшой искусственной задержкой (человекоподобно), а не мгновенно; индикатор «бот думает».
- Возможность отменить ход (takeback) — только против бота.
- Движок скрыт за интерфейсом `ChessEngine` (`init`, `setLevel`, `bestMove(fen, timeMs)`, `stop`, `dispose`), чтобы заменить реализацию (Stockfish WASM ↔ собственный движок) без изменений остального кода.
- Бот — обычный «соперник» с точки зрения партии: ходы приходят тем же протоколом, что и от человека (§5.1).

### 3.6 Гость и сессия

- В MVP единственный вид пользователя — **гость**. Вход и регистрации нет.
- При первом заходе создаются `id` (UUID) и случайный ник вида «Смелый конь»; аватар генерируется из `id` (цвет/градиент + инициалы).
- Гость может сменить ник (в шапке или при создании игры); данные хранятся в `localStorage`. Очистка браузера = новая личность (это ожидаемо, о чём сообщается пользователю).
- Личность игрока в партии: `{ kind: 'guest' | 'user', id, displayName, avatar }`. Тип `'user'` заложен в контракте, но в MVP не используется.
- **Задел:** приложение получает «кто я» только из `entities/session`, а не читает `localStorage` напрямую; при подключении к комнате в `connect` передаётся идентичность и необязательный токен (в MVP его нет). Формы входа, профиль и guard'ы маршрутов — после MVP (§10).

### 3.7 Страницы

| Маршрут     | Назначение                                                       | Доступ |
| ----------- | ---------------------------------------------------------------- | ------ |
| `/`         | Главная: создать игру, играть с ботом, локально, недавние партии | все    |
| `/game/:id` | Онлайн-партия / ожидание соперника                               | все    |
| `/bot`      | Настройка и партия с ботом                                       | все    |
| `/local`    | Локальная партия                                                 | все    |
| `*`         | 404                                                              | все    |

## 4. Нефункциональные требования

- **Производительность:** 60 fps при перетаскивании и анимациях; первичная загрузка < 200 КБ gzip JS; движок и страницы аккаунта — lazy-чанки.
- **Адаптивность:** от 360 px до десктопа; доска квадратная и помещается во viewport; touch-first.
- **Доступность:** доска — `role="grid"`, клетки доступны с клавиатуры, фигуры с `aria-label`, live-region для объявления ходов; учёт `prefers-reduced-motion`, `prefers-reduced-transparency`, `prefers-contrast`; контраст текста ≥ 4.5:1 на стекле в **обеих** темах.
- **Браузеры:** последние 2 версии Chrome, Safari, Firefox, Edge; iOS Safari 16+.
- **Безопасность (фронт):** при появлении реальной авторизации токены не хранятся в `localStorage` (целевая схема — httpOnly cookie, фронт работает через `AuthService` и не видит токен); входные данные протокола валидируются Zod; нет `dangerouslySetInnerHTML`; ники экранируются и ограничены по длине/символам.
- **Тестирование:** unit (Vitest), компонентные (Testing Library), e2e (Playwright): партия двух игроков в двух контекстах, партия против бота, смена ника гостя.
- **Качество кода:** TypeScript `strict`, oxlint, Prettier, Steiger, CI на каждый PR.
- **i18n:** RU/EN с первого дня.

## 5. Ключевые архитектурные решения

### 5.1 Транспорт

UI не знает, как ходы попадают к сопернику. Всё идёт через интерфейс в `shared/api`:

```ts
interface GameTransport {
  connect(gameId: string, identity: PlayerIdentity, auth?: SessionToken): Promise<void>
  disconnect(): void
  send(msg: ClientMessage): void
  subscribe(handler: (msg: ServerMessage) => void): () => void
  onStatusChange(
    handler: (s: 'connecting' | 'open' | 'reconnecting' | 'closed') => void,
  ): () => void
}
```

Реализации:

1. **`LocalTransport`** — hot-seat, без сети.
2. **`BroadcastChannelTransport`** — «онлайн» между вкладками одного браузера.
3. **`WebSocketTransport`** — заглушка с тем же контрактом; реализуется вместе с бэкендом.

**Кто «сервер» в моках.** Транспорт только передаёт сообщения. Авторитетную логику (проверка ходов, часы, определение результата) выполняет отдельная фича **`host-game`** (`features/host-game`), использующая `entities/game` и `entities/clock`. В режиме двух вкладок хостом становится создатель комнаты; в режиме бота хостом является локальная сторона, а «второй игрок» — адаптер движка, который слушает `state` и отвечает сообщением `move`. Когда появится бэкенд, `host-game` просто не запускается на клиенте — его роль занимает сервер.

Протокол (Zod-схемы в `shared/api`):

- Клиент → сервер: `join {identity, color?}` (повторный `join` — resync), `move {from,to,promotion}`, `resign`, `offerDraw`, `answerDraw {accept}`, `rematch`, `takeback` (бот), `ping`.
- Сервер → клиент: `state {status, startFen, fen, moves, clock, result, players, you, drawOffer}` (персональное: `you` — цвета получателя, в hot-seat оба), `moved {ply, san, move, fen, clock}`, `drawOffered {by}`, `drawDeclined`, `rematchRequested {by}`, `gameOver {result, reason, clock}`, `opponentPresence {color, online}`, `error {code}`.
- Сообщения хоста и клиента ходят через две стороны транспорта: `GameTransport` (клиент, как выше) и `HostTransport` (`onMessage(clientId, msg)`, `send`, `broadcast`, `onClientDisconnect`) — её слушает `host-game`. `clientId` выдаёт транспорт, он уникален для каждого соединения.

**Принцип:** хост авторитетен. Клиент делает оптимистичный ход, итоговое состояние приходит из `state/moved`; при расхождении — откат (клиент запрашивает `state` повторным `join`).

**hot-seat** — тот же путь: за экраном один клиент, а хост создан с `hotSeat` — места заняты сразу, а от имени нужной стороны (чей ход; кто отвечает на ничью) выступает любой клиент.

### 5.2 Сессия и личность (задел под авторизацию)

В MVP реализуется только гость, но приложение уже общается с «сессией» через интерфейс в `shared/api`:

```ts
interface AuthService {
  getSession(): Session // в MVP всегда guest
  updateGuestProfile(patch: { displayName: string }): Session
  subscribe(handler: (s: Session) => void): () => void
  getTransportAuth(): SessionToken | undefined // для handshake транспорта; в MVP undefined
  // после MVP: signIn / signUp / signOut
}
```

Реализации: `GuestAuthService` (MVP: id и ник в `localStorage`), позже `HttpAuthService` под реальный бэкенд.

Как это встраивается:

- `entities/session` — стор сессии и селекторы (`useSession`); единственное место, где приложение узнаёт «кто я».
- `app/providers` — внедрение `AuthService` и `GameTransport`.
- Транспорт получает идентичность (и токен, когда он появится) из сессии при `connect`.
- Чтобы добавить вход позже, нужно: реализовать `HttpAuthService`, расширить интерфейс методами `signIn/signUp/signOut`, добавить страницы и route guard'ы. Партии, игры, доска и транспорт при этом не меняются.
- Привязка партий гостя к аккаунту после регистрации — на уровне будущего `signUp(data, guestId)`.

## 6. Дизайн: liquid glass

### 6.1 Визуальный язык

- Фон: насыщенные градиентные «блобы» с медленной анимацией — за стеклом должно быть что преломлять.
- Стеклянные поверхности: `backdrop-filter: blur() saturate()`, полупрозрачная заливка, тонкая светлая обводка, верхний блик, мягкая тень.
- Скруглённые формы, «капельные» кнопки, упругая реакция на hover/press.
- Опционально — рефракция через SVG `feDisplacementMap` (Chromium), фолбэк на blur в Safari/Firefox.

### 6.2 Темы

- **Светлая** и **тёмная**, плюс режим «как в системе» (по умолчанию); выбор сохраняется.
- Всё через токены (CSS custom properties) на `:root[data-theme]`: цвета фона и блобов, заливка/обводка/тень стекла, палитра доски и фигур, акценты подсветок.
- Переключение без мерцания при загрузке (тема применяется до первого рендера).
- Каждая тема проходит проверку контраста отдельно; стекло в тёмной теме — не «светлая плашка на тёмном».

### 6.3 Доска

- Клетки — полупрозрачные светлые/тёмные оттенки, различимые на любом фоне; контраст клеток важнее прозрачности.
- Стекло накладывается на **контейнер доски**, а не на каждую из 64 клеток (иначе 64 `backdrop-filter` убьют fps).
- Подсветки (выбор, ходы, последний ход, шах) — свечение цветом акцента, не сплошная заливка.

### 6.4 Фигуры (собственная отрисовка)

- 12 фигур (6 типов × 2 цвета), вручную нарисованные SVG, единый стиль «стеклянных» фигур: градиентная заливка, внутренний блик, тонкая обводка, мягкая тень.
- Единая сетка (`viewBox="0 0 100 100"`), одинаковые оптические размеры и базовая линия; силуэты различимы на малом размере (≥ 32 px) и в оттенках серого.
- Белые и чёрные фигуры остаются различимыми на всех клетках в обеих темах — проверяется визуально и по контрасту.
- Цвета и градиенты берутся из токенов темы (`currentColor`/CSS-переменные), а не зашиты в SVG.
- Каждая фигура — отдельный React-компонент или `<symbol>` в спрайте (решается на этапе 3 по замеру производительности).
- До готовности финальных фигур используются упрощённые силуэты-заглушки, чтобы не блокировать разработку доски.

### 6.5 UI-кит (`shared/ui`)

`GlassPanel`, `GlassButton`, `GlassIconButton`, `GlassModal`, `GlassTabs`, `GlassToggle`, `GlassTooltip`, `GlassToast`, `GlassSegmentedControl`, `GlassInput` (смена ника), `GlassAvatar`. Все значения — из токенов.

### 6.6 Деградация

- Нет `backdrop-filter` / `prefers-reduced-transparency` → плотная полупрозрачная заливка без blur.
- `prefers-reduced-motion` → без анимации фона и пружин, ходы мгновенные.
- Слабые устройства → флаг «упрощённое стекло».

## 8. Структура (FSD)

Слой импортирует только из нижележащих; слайсы одного слоя друг друга не импортируют (исключение — `@x` в `entities`).

│  ├─ game-result-modal/
│  ├─ create-game-panel/

├─ features/
│  ├─ make-move/
│  ├─ promote-pawn/

│  ├─ clock/

Правила:

- Публичный API слайса — только через `index.ts`.
- `chess.js` не выходит за пределы `entities/game`; Stockfish — за пределы `entities/bot`.
- `GameTransport` и `AuthService` внедряются через контекст в `app`; фичи работают с интерфейсами.

## 9. Критерии приёмки MVP

1. Две вкладки браузера могут сыграть полную партию по ссылке, включая рокировку, взятие на проходе и превращение.
2. Партия против бота на всех уровнях: бот ходит легально, UI не подвисает, есть takeback, все исходы определяются.
3. Все виды окончания партии корректно определяются и показываются.
4. Часы синхронны между клиентами (расхождение < 300 мс), падение флага обрабатывается.
5. Закрытие и открытие вкладки восстанавливает партию.
6. Гость создаётся автоматически, ник можно сменить, он сохраняется между сессиями; приложение получает личность только через `entities/session`, так что замена `GuestAuthService` на другую реализацию не требует правок вне `app` и `shared/api`.
7. Обе темы (светлая, тёмная) и режим «как в системе» работают, без мерцания при загрузке; контраст ≥ 4.5:1.
8. Все 12 фигур нарисованы и одинаково читаются в обеих темах на любых клетках.
9. Адаптив 360 px – десктоп; деградация для reduced-transparency / reduced-motion.
10. Lighthouse: Accessibility ≥ 95, Performance ≥ 90 (десктоп).
11. Steiger и `tsc --noEmit` без ошибок; покрытие `entities/game`, `entities/clock`, `host-game` ≥ 90%.

## 10. Фазы после MVP

- Реальный `WebSocketTransport` и `HttpAuthService` при появлении бэкенда.
- **Авторизация:** вход/регистрация (метод выбирается вместе с бэкендом), профиль, история партий, route guard'ы, привязка партий гостя к аккаунту.

## 11. Принятые решения и открытые вопросы

Принято:

3. **Темы:** светлая и тёмная обе входят в MVP.
4. **Авторизация:** в MVP только гость, задел через `AuthService` и `entities/session`.
